可以。建议拆成两个独立交付：

1. **独立工具 `jc-slide-studio`**：负责 Markdown 解析、HTML 渲染、实时编辑、双向定位和可视化回写，有自己的 Git 仓库与版本。
2. **轻量 jc-slides skill**：负责研究汇报的写作流程、内容判断和工具调用，通过稳定接口连接 Studio。

下面给出完整开发与迁移计划。名称和目录是建议值，本次不创建文件或执行迁移。

**一、先确定代码、内容和规则的归属**

最重要的是：**工具应能脱离 skill 独立运行，skill 不再维护另一套渲染实现。**

| 内容 | 最终归属 |
|---|---|
| Markdown 方言解析、校验、源码映射 | Studio |
| HTML 渲染、播放器、章节导航、动画 | Studio 或其版本化依赖 |
| 编辑器、预览服务、文件保存、可视化回写 | Studio |
| 主题、字体、资源打包 | Studio 的资源管理层 |
| 学术汇报的论证、证据、讲稿和制作流程 | jc-slides skill |
| ARA/story 定位、项目归属与归档规则 | skill 及既有治理工具 |
| outline、draft、图件、项目样式、成片 | 各自的 story 目录 |

源稿仍留在现在的研究项目中。Studio 打开指定文件，不要求把汇报搬到工具仓库。

同时明确三层状态：

- **持久来源**：Markdown，以及它显式引用的样式和图件源。
- **编辑状态**：内存中的文档、语法树、选区、撤销历史和版本。
- **生成物**：HTML、缩略图、源码映射缓存。

语法树和 HTML 都可以重新生成，不成为另一份需要同步维护的权威稿。

**二、第一部分：独立开发 Studio**

**1. 仓库与安装方式**

建议独立目录：

```text

```

不放进博士论文仓库，也不放在 skill 安装目录。目录正式创建前检查已有项目与命名冲突。

建议结构：

│  ├─ providers/             # 主题、播放器、图件适配
│  └─ web_dist/              # 发布包内的前端构建产物
├─ web/

│     ├─ editor/

Git 管理源代码、测试样例、依赖锁文件和文档；环境目录、运行缓存、真实汇报、截图测试产物不进入仓库。

开发阶段使用独立环境。发布阶段把构建好的前端打入 Python 安装包，**日常使用只需启动一个命令，不必另外运行 Node 开发服务器**。

提交、远程仓库创建与推送按实际授权执行，不在本次计划中自动执行。

**2. 技术栈**

建议采用：

| 部分 | 选择 | 原因 |
|---|---|---|
| 核心引擎 | Python，逐步迁出已有实现 | 保留现有 Markdown 和渲染兼容性 |
| 本地服务 | FastAPI | 承载文件接口、编辑会话及消息 |
| 工作台 | TypeScript＋React | 管理编辑器、导航和属性面板 |
| Markdown 编辑器 | CodeMirror 6 | 支持事务、选区、撤销和扩展 |
| 前端构建 | Vite | 将工作台打包为静态资源 |
| 预览 | iframe＋现有播放器 | 保持实际成片效果 |
| 测试 | pytest＋Playwright | 分别验证引擎与浏览器交互 |

FastAPI 可以提供静态文件与 WebSocket；Vite 可将工作台构建为可分发静态文件，适合上述单进程运行方式。[FastAPI 静态文件](https://fastapi.tiangolo.com/tutorial/static-files/)、[WebSocket](https://fastapi.tiangolo.com/advanced/websockets/)、[Vite 构建](https://vite.dev/guide/build.html)

第一版不更换 Markdown 方言，也不同时重写播放器。

**3. 先迁出引擎，建立可独立运行的基线**

从现有 jc-slides 中迁移以下能力：

| 现有模块 | Studio 中的职责 |
|---|---|
| `build_deck.py` | 拆分为解析、校验、渲染和 CLI |
| `deck_delivery.py` | 离线资源打包与原子输出 |
| `deck_preview.py` | 文件监听、构建调度、预览 |
| `chapter_navigation.py` | 章节与目录生成 |
| `render_html.cjs` | 截图与视觉检查支持 |
| 初始化、骨架相关脚本 | 放入工具的模板初始化模块 |

`story_output.py` 中项目专属的 ARA 定位逻辑与通用输出逻辑要分开：工具接受明确的源文件和输出位置；skill 负责按照项目规则解析这些路径。

现有主题和播放器依赖也要处理。当前构建器通过 skill 的相邻目录寻找 epool-slides，这种路径关系不能成为独立工具的安装条件。

具体做法：

- 核对主题、字体、播放器的来源、许可与依赖。
- 将允许分发的必要资源以明确版本随工具发布。
- 保留自定义资源包接口。
- 记录上游版本及校验值。
- 禁止运行时偷偷回退到某个用户的 skill 目录。

**验收：在无法访问原 skill 目录的环境中，工具仍能检查、渲染和预览测试稿。**

**4. 建立源码映射，作为编辑功能的基础**

解析器应输出原始文档、语法树和映射，至少包含：

```text
documentRevision
slideId
nodeId
nodeType
sourceRange
editableFields
```

设计要求：

- 页面 ID 稳定，标题和页序变化不改变身份。
- 节点映射与文档版本绑定，旧预览不能修改新文档。
- 源码位置覆盖完整文件，包括 frontmatter 和非渲染工作区。
- 修改局部字段时仅替换对应片段，保留其他内容的排版和注释。
- 自动生成的目录项映射到章节源标题。
- 缺少显式 ID 的旧稿仍可打开；需要补 ID 时，通过可撤销的源码修改完成。
- 不把所有段落 ID 都写成 Markdown 注释；节点映射优先维护在编辑会话中。

需要专门测试 Windows 换行、中文、emoji、重复段落、嵌套容器，以及前端和 Python 的字符偏移转换。你的“圆＋🔴；方＋🟥”例子应进入测试样例。

**验收：点击任何已支持的可编辑元素，都能准确找到源码；修改后未涉及的文本保持原样。**

**5. 实现文档服务与保存机制**

每次编辑都形成有版本的事务：

```text
操作来源＋基础版本＋修改内容 → 新版本
```

操作来源可以是 Markdown 输入、页面可视化编辑、属性面板或外部文件变更。

需要实现：

- 自动保存和手动保存。
- 原子写入，保存失败时保留编辑缓冲区。
- 浏览器刷新后的未保存内容恢复。
- 文档修改版本与成功预览版本分别显示。
- 监听 agent、VS Code 等对源稿和资源的外部修改。
- 有待保存内容时检测冲突，不直接覆盖。
- 自己保存产生的文件事件不重复触发编辑循环。
- 默认一个写入会话，其他会话只读，避免第一版引入多人协作复杂度。

保存接口限定当前会话绑定的文件和资源范围；本地服务使用会话令牌、来源校验和版本检查。

**验收：外部改文件、保存失败、浏览器刷新和连续快速输入都不会静默丢失内容。**

**6. 实现编辑工作台**

第一版界面包括：

| 组件 | 功能 |
|---|---|
| 页面导航 | 章节、页标题、当前页、错误标记 |
| Markdown 编辑器 | 全文、当前页聚焦、讲稿折叠、搜索 |
| 预览 | 固定画布比例、缩放、切页、动画检查 |
| 属性面板 | 当前页版式、动画、讲稿及选中元素属性 |
| 状态栏 | 保存状态、构建状态、当前版本、错误 |

首批交互规则：

- 光标进入某页，预览跟随。
- 预览切页，源码定位到该页。
- 点击页面元素，源码选中对应范围。
- 当前主动操作侧控制联动，避免互相跳转。
- 提供“锁定预览”。
- 编辑模式显示全部内容；演示检查模式保留动画初态和步骤。
- 工作区和制作备注没有页面对应时明确提示，不跳到错误幻灯片。

**验收：不依赖复制页码或手工搜索，就能完成逐页修改。**

**7. 实现实时构建**

推荐分两步。

第一步复用全量构建：

- 输入停止后短暂防抖。
- 构建队列合并重复请求。
- 只发布最新有效版本。
- 刷新预览 iframe，保留工作台、光标和编辑器滚动位置。
- 按稳定 ID 恢复当前页。
- 动画结构改变时，将旧步骤调整到有效范围。
- 构建失败继续显示上一版，同时标记预览落后。

第二步依据实测优化：

- 缓存图片和主题资源。
- 编辑预览使用可缓存的资源 URL。
- 正式导出时再内嵌成离线 HTML。
- 仅在确有收益时增加单页更新。
- 主题、页序、目录等全局变化仍触发完整更新。

性能目标可以设为：代表性稿件中，普通文字修改后预览更新的 P95 不超过约 1 秒；这是验收目标，需在实际机器上测量，不预先承诺。

**8. 实现受控可视化编辑**

第一批支持：

| 操作 | 回写内容 |
|---|---|
| 修改标题 | 对应标题文本 |
| 修改普通段落、列表项 | 对应内容块 |
| 修改图注 | 图片标题字段 |
| 替换图片 | 图片引用与资源 |
| 修改讲稿 | `::: notes` 内容 |
| 切换版式、动画 | 页面指令与 fragment 配置 |

可视化操作应先生成修改请求，由文档层检查节点、字段和版本，再进入编辑器事务。不要让预览 DOM 直接写磁盘。

复杂行内格式第一版采用块级编辑弹层或定位源码，避免直接编辑破坏链接、粗体和公式。

以下功能后置：

- 自由拖拽排版。
- 任意 CSS 编辑。
- 表格合并、复杂结构重组。
- Pele 图节点和连线编辑。

Pele 后续作为资源适配器接入：有图源时修改图源并重建；只有 SVG 时支持显示、替换和定位来源，不推断恢复图的结构。

**验收：页面改字与 Markdown 改字使用同一套撤销历史；重新启动后结果可完全重建。**

**9. 固定工具接口**

以下是拟议接口，开发完成后才可用：

```text
jc-slide-studio doctor --json
jc-slide-studio check <source.md> --json
jc-slide-studio render <source.md> --out <directory> --json
jc-slide-studio preview <source.md> --out <directory>
jc-slide-studio edit <source.md> --out <directory>
```

`doctor` 返回版本、协议版本、Markdown 方言版本、功能能力和资源包状态。

其他命令返回机器可读结果，例如：

```json
{
  "protocolVersion": 1,
  "ok": true,
  "source": "绝对源文件路径",
  "output": "实际生成的HTML绝对路径",
  "slideCount": 51,
  "diagnostics": []
}
```

同时规定：

- JSON 输出与日志分流。
- 失败有明确退出码。
- 长驻服务报告就绪地址、会话和状态。
- 输出名称从明确配置或源目录名推导；单文件默认不叫 `index.html`。
- 配置优先级为 CLI 参数 → 项目配置 → 工具默认值。
- 自定义 CSS 通过配置声明，无需复制主题到临时目录再修改。

引擎负责语法和结构检查；“论证充分、讲稿合适、研究结论准确”仍由 skill 和人工判断。

**10. 测试、打包与独立验收**

| 测试组 | 必须覆盖的行为 |
|---|---|
| 渲染兼容 | 旧稿页数、目录、notes、动画、资源与布局 |
| 源码映射 | 重复文字、中文、emoji、CRLF、嵌套容器 |
| 保存一致性 | 版本冲突、失败恢复、外部修改、撤销 |
| 双向定位 | 插页、删页、移页、改标题后的定位 |
| 构建调度 | 连续输入、过期结果、缺图后恢复 |
| 可视化回写 | 修改正确字段，未改区域保持原样 |
| 发布包 | 无原 skill 目录、无 Node 开发服务器也可运行 |
| 正式成片 | 离线可播放，不携带编辑工作台和源码映射 |

浏览器回归用 Playwright 验证，关键页补视觉截图，不能只检查 DOM 是否存在。[Playwright 官方文档](https://playwright.dev/docs/intro)

真实博士汇报在本地副本中做接入验收；工具仓库只保留可公开的最小样例。

**三、第二部分：更新 jc-slides 并接入 Studio**

这部分在工具独立验收通过、CLI 协议稳定后启动。

**1. 精简 skill 的职责**

保留现有学术制作流程：

```text
plan → fill → review → script → design → check → render
```

前五步由 agent 按规范完成；最后两步调用 Studio。检查失败或视觉不合适时，仍回到受影响的写作或设计阶段。

新增“打开编辑工作台”操作，区别于现有“由 agent 修改幻灯片”的 `edit` 流程。

| 用户需求 | skill 动作 |
|---|---|
| 从 outline 写 draft | 执行写作规范 |
| 检查或生成 HTML | 调用 Studio |
| 打开实时编辑器 | 调用 Studio `edit` |
| 帮我改某页 | 定位源稿、修改、调用检查和渲染 |
| 检查视觉效果 | 调用截图能力并审查 |
| PPTX 导出、归档 | 保留既有交付规则，调用相应工具 |

**2. 修改 skill 文件**

| 文件 | 计划变化 |
|---|---|
| `SKILL.md` | 说明工具依赖、职责边界和入口 |
| `ops.json` | 将构建命令切换为 Studio；新增工作台操作 |
| `html/MODULE.md` | 使用新检查、渲染、预览命令 |
| `edit/MODULE.md` | 加入双向定位、回写范围与冲突处理 |
| `delivery/MODULE.md` | 对接实际产物路径，保持导出归档能力 |
| `references/md-spec.md` | 指向工具权威规范，只保留写作摘要 |
| 预览和局部编辑说明 | 更新工作台操作方式 |
| `CHANGELOG.md` | 记录接口迁移与最低兼容版本 |

Markdown 语法规范由工具仓库维护，skill 不再复制一份完整且容易漂移的规范。

**3. 工具发现与版本约束**

skill 应按以下顺序发现工具：

1. 显式配置的可执行文件。
2. 已安装的 `jc-slide-studio` 命令。
3. 找不到时给出安装或修复说明。

不能自动假设源码仓库一定在 `E:\05code`。

调用前检查协议与能力；安装版本不兼容时清楚报错，不自动升级，也不自动改写旧稿。

skill 最多保留一个薄适配器，负责参数、路径和结果解析。解析、渲染、监听、编辑服务都只保留在工具仓库。

**4. 分阶段迁移旧脚本**

迁移顺序：

1. 冻结旧引擎基线并记录版本。
2. 新工具与旧引擎针对相同样例对照运行。
3. skill 新入口全部切到 Studio。
4. 旧脚本暂时变成转发入口，提示迁移。
5. 验证所有已登记调用方后，移除旧业务实现。

过渡期间允许兼容入口存在，但不长期维护两套引擎。

已有 draft 中写死的构建脚本、临时主题目录和 `--filename index.html` 应列入迁移清单。工具和 skill 验收完成后再更新这些项目指令，不在开发前顺便改动研究稿。

**5. skill 接入验收**

必须实际完成以下流程：

- 根据指定 draft 检查并生成命名正确的 HTML。
- 打开工作台，修改 Markdown，预览更新。
- 点击预览页，源码定位正确。
- 在页面修改标题，源稿写回并可撤销。
- 外部编辑源稿，工作台正确接收或报告冲突。
- 离开工作台后，仅用 CLI 重建，得到一致结果。
- 工具缺失或版本不兼容时，返回清楚错误。
- 原有导出与归档操作仍能完成。

**四、里程碑与依赖关系**

| 里程碑 | 独立交付物 | 完成条件 |
|---|---|---|
| M0：契约与仓库设计 | 架构、方言基线、CLI/API 契约、测试样例 | 边界、依赖和兼容策略明确 |
| M1：独立引擎 | check/render/preview 命令 | 脱离 skill 目录可运行，旧稿兼容 |
| M2：编辑工作台 | 自动保存、实时预览、页级双向定位 | 文件修改与预览版本一致 |
| M3：可视化编辑 | 元素定位、受控回写、统一撤销 | 页面修改可从源稿重建 |
| M4：工具发布包 | 可安装包、文档、独立环境测试 | 普通使用不依赖开发环境 |
