## 0. 尚未实施 / 待定案

- **前端接入方式**：云端 SDK 是浏览器端直连 `/.cloud/**`，登录/数据不再走自建
  `/api/auth/*`、`/api/decks/*`；但渲染引擎是 Python 的，必须保留一个无状态后端。
  因此只能走「混合架构」：Python 服务托管静态前端 + 提供 `/api/render`，
  前端直连云端 Auth / Database。
- **Origin 约束**：SDK 校验请求 Origin 与发布域名精确匹配，`localhost` 跑不通云端登录；
  接入后必须发布到保留域名才能验证关键路径。
- **登录方式**：云端 `signUp` 需要 OTP 带来的 `verificationToken`，不能像本地版那样
  「邮箱 + 密码一步注册」。可选：纯邮箱验证码，或「验证码注册 + 密码登录」。
- **数据迁移**：云端 PostgreSQL 与本地 SQLite 不互通，已有本地 deck 需另写导入。
- **线上部署**：明确延后，需用户单独授权发布；发布时必须复用同一个 `applicationId`
  作为 `appId`，否则域名变化会导致云端登录失效。
- §6.3 附件存储、§10 P3 图片上传：未做，Markdown 中的相对图片路径在库模式下仍需另配。
- 分享只读链接、找回密码、多端实时协同、版本恢复 UI：未做。
- 本地自建版登录方式为「邮箱 + 密码」；云端版按上条重新定案。

## 1. 目标与非目标

### 目标

1. 用户可登录后看到属于自己的**幻灯片库**（多份 deck），而不是一次只能打开一个本地文件。
2. deck 的 Markdown 源文与其引用附件存放在服务器，换机器、换浏览器都能继续编辑。
3. 保留现有「本地 CLI 工作台」形态：离线、单文件、零依赖的运行方式不被破坏。
4. 数据按用户隔离，服务端强制（不是前端过滤）。

### 非目标（本期不做）

- 多人实时协同编辑（OTRS/CRDT）。当前 `revision` 采用乐观锁，冲突时提示而非自动合并。
- 移动端适配、PPTX 导出。
- 对外分享只读链接（留接口位置，见 §8 开放问题）。

## 2. 现状（As-Is）

```
浏览器 (web/src/App.tsx)
  │  GET/PUT /api/document        单文档，无身份
  │  POST /api/patch
  │  WS  /ws                      只有 RELOAD 广播
  ▼
FastAPI (server/app.py)  ── 进程级单例 StudioState.source_path ──► 磁盘上的一个 .md
  │  GET /preview/workbench?revision=N
  ▼
render/engine.py (Jinja2 + 36 主题 + 字体 + Reveal.js 运行时)
```

关键事实（决定了改造边界）：

| 事实 | 影响 |
|---|---|
| 渲染只接受**磁盘路径** `render_deck(path)`，附件按 `path.parent` 解析 | 云端模式必须新增「按内容渲染」入口，否则无文件可渲染 |
| `StudioState` 是**进程级单例**，只有 `source_path` 一个文档 | 多用户/多 deck 必须改为无状态或按请求传参 |
| 前端 `EditorSession` 硬编码 `fetch('/api/document')` | 需要抽出存储适配层，否则本地/云端两套逻辑会分叉 |
| 编辑器内核（CodeMirror + AST 映射）与存储无关 | 可直接复用，是本方案的支点 |

## 3. 核心约束

1. **渲染引擎在 Python**（Jinja2 模板、字体资产、`apply_node_patch` 等），前端只做编辑与壳。要么把 Python 部署上去，要么把渲染重写成 JS（≈ 重写整个 `render/` 与 `document/`，不作为本期选项）。
2. **托管后端要求发布域名精确匹配 Origin**：`publishableKey` 本身无权限，服务端校验请求来源域名。因此**云端能力在 localhost 上无法验证**，必须在发布后的 HTTPS 域名上跑通（本地开发继续走本地文件模式）。
3. **一个应用 = 一个云环境**，数据不跨应用共享。

## 4. 方案对比

| | A. 云端 Web 版（推荐） | B. 本地工具 + 云同步 | C. 全自建 |
|---|---|---|---|
| 形态 | 发布到 HTTPS 域名的 Web 工作台，登录后选 deck | 仍是 `jc-slide-studio edit`，额外加「上传/拉取」 | 自己的 FastAPI + Postgres + Cookie 会话，部署到腾讯云 CVM |
| 账号 | 托管 Auth（邮箱/手机验证码、WorkBuddy 账号） | 同 A | 自建（密码哈希、邮件发送、找回流程都要自己写） |
| 存储 | 托管 PostgreSQL + 对象存储 | 同 A | 自建库 + COS/本地盘 |
| 渲染 | Python 无状态渲染服务（部署在同一应用） | 本地 Python（不变） | 自建 Python 服务 |
| 前端改动 | 大：加路由、登录页、库页、存储适配层 | 中：存储适配层 + 同步 UI | 大 |
| 后端改动 | 中：`/api/render` + 去单例化 | 小 | 大（新增整个账号域） |
| 无需运维 | ✅ | ✅ | ❌ 服务器、域名、备案、HTTPS、备份自理 |
| 主要风险 | localhost 无法调试云功能 | 依旧要本地起进程，云端只是备份 | 密码/邮件/安全问题全自己扛 |

**结论：选 A，同时保留本地模式作为离线路径。** B 作为 A 的一个子集（P4 的导入/导出），C 只在「不想绑定平台」时启用，数据模型与前端适配层可平移。

## 5. 目标架构（To-Be）

```
浏览器（同一份 web/ 构建产物，两种运行态）
  ┌───────────────────────────────────────────────┐
  │ shell: /login → /library → /workbench/:deckId │
  │                                               │
  │  EditorSession ──► DeckStore (接口)           │
  │                     ├── LocalFileStore  → /api/document      （本地模式）
  │                     └── CloudStore      → cloud.auth/database/storage（云端模式）
  └───────────────────────────────────────────────┘
        │ 预览：POST /api/render { content, theme }
        ▼
  FastAPI（无状态）
    POST /api/render     content → 单页 HTML（供 iframe srcdoc）
    GET  /preview/*      主题/字体/fx 静态资产
    GET  /api/document   仅本地模式（读 state.source_path）
```

要点：

- **数据面全部由前端 SDK 直连**（Auth 自动注入会话），Python 不碰数据库、不持有服务端密钥。
- **Python 只做纯函数渲染**：输入 md 文本，输出 HTML。这样它天然可水平扩展、无需鉴权，也不存在「后端怎么验证 token」的复杂度。
- **本地模式完全保留**：`jc-slide-studio edit deck.md` 走的还是 `LocalFileStore`，不要求登录。

## 6. 数据模型

### 6.1 表结构（PostgreSQL，托管环境）

```sql
create table decks (
  id               bigint generated always as identity primary key,
  owner_id         text   not null default auth.uid(),
  title            text   not null,
  slug             text   not null,
  theme            text,
  layout           text,
  slide_count      int    not null default 0,
  current_revision int    not null default 1,
  content_hash     text,                          -- sha256(归一化后 md)，用于同步判重
  created_at       timestamptz not null default now(),
  updated_at       timestamptz not null default now(),
  deleted_at       timestamptz,                   -- 软删除，误删可恢复
  unique (owner_id, slug)
);

create table deck_revisions (
  id         bigint generated always as identity primary key,
  deck_id    bigint not null references decks(id) on delete cascade,
  owner_id   text   not null default auth.uid(),
  revision   int    not null,
  content    text   not null,                     -- 完整 md 快照，不做 diff
  note       text,
  created_at timestamptz not null default now(),
  unique (deck_id, revision)
);

create index decks_owner_updated on decks (owner_id, updated_at desc);
create index revisions_deck_rev  on deck_revisions (deck_id, revision desc);
```

设计取舍：

- **全文快照而非 diff**：单个 deck 通常 20–200 KB，全量快照让恢复、导出、冲突比对都变成一次读，避免 diff 合并的复杂度。保留最近 50 个 revision（超过后按时间清理）。
- **`owner_id` 为 `text`**：与 `auth.uid()` 返回类型一致。
- **`slide_count` 冗余**：库列表页不用解析 md 就能显示页数，写入时随内容更新。
- **软删除**：`deleted_at`，列表默认过滤。

### 6.2 行级安全（RLS）

每张用户表启用 RLS，策略统一为「本人可读写自己的行」：

```sql
alter table decks enable row level security;

create policy decks_select on decks for select using (owner_id = auth.uid());
create policy decks_insert on decks for insert with check (owner_id = auth.uid());
create policy decks_update on decks for update using (owner_id = auth.uid()) with check (owner_id = auth.uid());
create policy decks_delete on decks for delete using (owner_id = auth.uid());
```

`deck_revisions` 同构（`deck_id` 属主校验 + `owner_id = auth.uid()`）。

前端**永不发送 `owner_id`**，由 `DEFAULT auth.uid()` 填充。

### 6.3 附件存储

对象存储 bucket `deck-assets`，路径规范：

```
{owner_id}/{deck_id}/{sha1前8位}-{原始文件名}
```

Markdown 中的图片引用在上传后改写为**签名/公开 URL 的绝对地址**，从而摆脱「相对 base_dir」依赖——这也是让渲染服务无状态的前提。

## 7. 读写协议与冲突

### 7.1 打开 deck

```
1. cloud.auth.getSession() → 无会话则渲染登录页（强制门禁）
2. from('decks').select('*').eq('id', deckId).single()
3. from('deck_revisions').select('content').eq('deck_id', deckId)
     .eq('revision', current_revision).single()
4. EditorSession.load(content)
```

### 7.2 保存（乐观锁）

```
1. 防抖 380ms（沿用现有节奏）
2. from('deck_revisions').insert({ deck_id, revision: n+1, content }).select()
     唯一约束冲突 → 说明别人先写了 → 进入冲突分支
3. from('decks').update({ current_revision: n+1, content_hash, slide_count, updated_at })
     .eq('id', deckId).eq('current_revision', n).select()
     返回空数组 → 冲突
4. 冲突 UI：显示「云端有更新」→ 三个选项：用云端覆盖本地 / 保留本地并另存为新 revision / 并排对比
```

## 9. 登录方式取舍

| 方式 | 优点 | 代价 | 适用 |
|---|---|---|---|
| 邮箱验证码（OTP） | 无需密码、无需短信配额、找回流程不存在 | 依赖收件箱；首次注册靠验证即建号 | **个人自用首选** |
| 手机短信验证码 | 国内体验最顺 | 短信配额与费用、需 provider 开通 | 有他人使用的可能时 |
| WorkBuddy 账号登录 | 一次授权，无需验证码 | 依赖平台账号；localhost 不可调试 | 团队内共用 |
| 微信登录 | 扫码即入 | 需要 provider 开关 + 发布域名 | 面向公众分享时 |

⚠️ 三种 OAuth（微信、WorkBuddy）在 localhost 一律被拒，只能在发布后的 HTTPS 域名验证；邮箱/短信验证码虽也受 Origin 校验，但仍需在发布域名上测。

## 11. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| localhost 无法验证云端登录 | 开发反馈环变慢，必须发布后才能测 | 本地模式保持可用；云功能每次改动后重新发布验证 |
| 发布环境是单端口 Python 服务 | 需要明确的启动命令与依赖安装（Jinja2/字体资产） | 提供 `deploy` 入口脚本 + 最小依赖集，字体资产随包分发 |
| 无状态渲染的冷启动/CPU | 编辑时预览延迟 | 前端 380ms 防抖 + `content_hash` 缓存 + 预览复用上次结果 |
| 图片相对路径 | 云端渲染取不到本地图 | P3 前所有附件强制走 bucket 绝对 URL，解析器保留原样透传 |
| 全文快照增长 | 单 deck 50 版会占空间 | 保留最近 50 版；超限清理最旧且非「手动命名」的快照 |
| 配额（用户数/行数/存储） | 触顶后写入失败 | 前端把 `quota` 错误显式呈现，不静默失败 |

## 12. 决策与剩余开放问题

已定案（本轮按此实现）：

| 项 | 结论 |
|---|---|
| 登录方式 | **邮箱 + 密码**（PBKDF2，会话 Cookie；未启用短信/OAuth） |
| 同步语义 | **服务端为主**，本地 `.md` 只做一次性批量导入 |
| 未登录试用 | 不提供；库模式强制登录门禁，本地 `edit` 模式无需登录 |
| 实现路线 | 先**本地自建后端**跑通全链路；托管云服务与线上部署**明确延后** |

仍需定案：

1. **是否接托管云服务**（Auth / PostgreSQL / 对象存储）。开通确认弹窗两次被关闭，未产生环境；
   若要接，只需把 `RemoteDeckStore` 换成 SDK 实现并补 `DeckStore` 之外的登录壳，编辑内核不动。
2. **线上部署目标**：自己的腾讯云 CVM / 轻量（域名、HTTPS、备案由本人办理），还是工作台一键发布。
3. **是否要分享只读链接**给他人看（会影响 `decks` 是否加 `visibility` 字段与公开读策略）。
4. **附件策略**：图片走对象存储还是本地持久盘（当前库模式下相对图片路径未处理）。
